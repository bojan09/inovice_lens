# InvoiceLens: final QA (Phase 6)

All numbers below were measured in this project's cloud session (headless Chromium via Playwright, Node 22, LibreOffice, poppler, python-docx/openpyxl, Lighthouse 13.6). Nothing is estimated or taken from a vendor. Where a check could not be run, it says so under "Not verified". Raw machine-readable results: `docs/qa/measured.json`, `docs/qa/lighthouse-summary.json`, `docs/qa/css-coverage.json` (regenerated by the test run / `scripts/css-coverage.mjs`).

## 1. Verdict

For the supported scope (English invoices, receipts and simple tables; images and PDFs; Chromium) the critical journeys work end to end and are covered by automated tests with real OCR, real downloads and independent readers. **Accuracy on real-world documents is unmeasured**: the only measurements are on a synthetic corpus produced by the same author as the extractor (see `docs/PHASE3.md`). Treat every extracted value as a suggestion to check against the original.

## 4. Critical journeys verified

Upload -> recognition -> review/edit -> export (all four formats) -> save project -> reload -> resume; batch with a broken file; pause/resume/cancel; offline after the first download; update of the service worker with a saved project; import/export of a portable project file in a fresh browser profile; deletion; low storage (injected quota error). Each is an automated test (`tests/browser/*.e2e.js`).

### Export recheck on representative samples (all four formats, independent readers)

For six corpus samples (invoice layouts A to D, clean and photo-simulated, plus a receipt), the test opens the editor, reads what the user sees, exports PDF, Word, Excel and CSV, re-opens each file with an independent tool and compares:

| Format | Reader | Compared |
|---|---|---|
| PDF (structured) | `pdftotext -layout` | every field value and every table cell appears as text |
| Word | python-docx | details table pairs and the line-item table equal the editor's |
| Excel | openpyxl | Total and every row total are **numeric cells** equal (in minor units) to the parsed editor text; the currency column matches |
| CSV | Python `csv` (UTF-8 BOM) | rows equal; amounts equal in minor units; currency in its own column |

Result: **6 of 6 samples pass for all four formats** (24 file/format checks). Earlier phases additionally verified: original-appearance PDF (`pdfimages`, page order/rotation, text layer), combined PDF / consolidated workbook / CSV, ZIP, Office package integrity, LibreOffice round trips.

**A defect found by this recheck and fixed:** line-item CSV/XLSX tables dropped the currency (amounts are plain numbers). A `Currency` column was added to the line-item tables (CSV, XLSX, consolidated).

## 5. Accessibility

- **axe-core: 0 violations** on every tested state: Convert (empty, files, rejected, recognized/review/failed cards), editor (every tab, both themes, desktop/390/320, with an error and an ambiguity showing), export dialog (every format/mode), Batch (with selection), Projects (empty and with a card), Save/Delete dialogs, Settings (all six sections). Light and dark. Lighthouse accessibility: 100 (mobile and desktop).
- **Keyboard-only journey** (test): Tab to Browse Files, Enter activates the picker, Tab to Review & edit, edit, Ctrl+Z/Ctrl+Shift+Z, tab arrows, open Export with the keyboard, choose a format, download, Esc closes and focus returns to the opener; the skip link works. A visible focus indicator was asserted at every stop. (Headless Chromium does not expose a keyboard-opened file chooser to Playwright, so that one step is proven by the file input receiving the activation.)
- **Touch targets** >= 44 px at 390 px for controls in the editor, Batch, Projects, dialogs and Settings (checkbox hit areas were enlarged after tests found 24 px).
- Reduced motion is honoured (OS setting and an explicit Settings switch).
- **Not verified:** real screen readers; browser zoom/text-size at 200%+ beyond the responsive layouts; high-contrast/forced-colors mode.

## 6. Performance (measured, one run each, cloud container)

Lighthouse (local static server, no CDN, no HTTP compression):

| | Performance | Accessibility | Best practices | SEO | FCP | LCP | TBT | CLS |
|---|---|---|---|---|---|---|---|---|
| Mobile preset | 99 | 100 | 100 | 100 | 1.7 s | 1.7 s | 0 ms | 0 |
| Desktop preset | 100 | 100 | 100 | 100 | 0.4 s | 0.4 s | 0 ms | 0 |

Not passing in Lighthouse: *bf-cache* (the dev server sends `Cache-Control: no-store`) and the *network dependency tree* insight (about 84 requests: the app is **unbundled ES modules**, about 380 KB of source across ~90 files; there is no build step). A real deployment should add compression, long-lived caching for versioned files, and could bundle; neither was done or measured here.

Sizes: app shell (HTML/CSS/JS/icons, precached) well under 1 MB; vendored libraries 11.5 MB (OCR engine+English data 6.7 MB, pdf.js 2.9 MB, export writers 1.9 MB), loaded only when used or when "Download for offline use" is pressed.

CSS coverage over a scripted tour of every screen and dialog (`scripts/css-coverage.mjs`): **81.8% of 69 KB used**. The unused remainder is mostly hover/focus/dark-token variants and states the tour does not reach (for example project cards and warning states). Two genuinely dead rules (`.spinner` + keyframes, `.soon`) were removed; the rest were reviewed and kept.

Throttled run (CDP, 4x CPU slowdown on the main thread, ~1.6 Mbit/s, 390x844 touch): editor opens in 0.8 s, typing a field value took 47 ms, first export ready in 0.5 s; **5 main-thread tasks over 200 ms, longest 570 ms** (that is the slowest observed stretch of work on the page during the journey; it was not traced to a single function and was not optimised). **Caveat:** CPU throttling does not slow the Web Worker that runs OCR and the OCR files may come from the service-worker cache, so the recognition times in `measured.json` are **not** a phone estimate. Real-device performance is unmeasured.

## 7. Security and privacy

- Strict CSP (`default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; ...`), no inline script or style. Static scan: no `eval`, `new Function`, `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `document.write` anywhere in `js/` or `index.html`; all text is set with `textContent`.
- **XSS test:** markup in file names, in a project name and inside the recognized text of an image is displayed literally in Convert, Batch, editor, export dialog, file names and Projects; no script runs; no CSP/console errors.
- **Input hardening test:** a PNG claiming 100000 x 100000 px, a truncated PNG, an executable renamed `.png`, an empty PDF, a `.txt` and an HTML-in-`.png` are all refused with a reason; the app stays usable. PDF scripting is disabled; ZIP project files are size-limited before inflating, strictly validated, and path traversal is rejected.
- **Network:** only same-origin GETs are made while recognizing, editing, exporting, saving, importing and deleting (asserted in several tests); no analytics, no accounts, no uploads.
- **Storage:** `localStorage` holds only the theme and settings preferences (validated allow-list, no file names or content); IndexedDB holds projects only after explicit consent; the service worker caches only static program files and never a user document (tested: no document name appears in any cache).
- **Supply chain:** libraries are vendored with pinned versions and sha512 integrity checks (`scripts/vendor.js`); `npm audit` reports 0 vulnerabilities for the dev dependencies.
- **Not verified:** a third-party penetration test, behaviour behind enterprise proxies, and malicious PDFs beyond the fixtures used (pdf.js is the parser of record).

## 8. PWA and offline

- Manifest, three icons (including a maskable one), `apple-touch-icon`, theme colours, service worker with a versioned shell cache and a separate versioned vendor cache. `sw.js` and `js/pwa-manifest.js` are **generated** from the files that exist (`npm run build:pwa`) and a unit test fails if they are stale.
- **Documented conditions:** the app opens offline after it has been loaded once online; recognition and export additionally need the vendored files, which are cached when first used or all at once via Settings > Storage & offline > "Download for offline use". **First open while offline is not possible.** Offline without the OCR files shows a clear message instead of failing silently. Verified by tests: offline reload; offline recognition of an image and a PDF; offline export of PDF, Word, Excel and CSV; offline save, reload and resume of a project; cold-offline failure; offline-without-files message.
- **Updates:** a new worker waits (it never swaps itself in under a running session); the page shows "Reload to update"; after applying it the old cache is removed and a project saved before the update still opens (tested with a changed worker version).
- Install prompt: the `beforeinstallprompt` path is wired to an "Install app" button but **could not be exercised in headless Chromium**; installation on real devices was not tested.

## 10. Not verified, unsupported, residual risks

- **Accuracy on real documents: unmeasured.** Synthetic-only figures (held-out 96.9% micro-F1 on 10 documents) say how the extractor handles one generator's variations. Real invoices (stamps, logos, multi-column layouts, other fonts, handwriting, non-English text, crumpled photos) will do worse.
- **Browsers:** Chromium only. Firefox and WebKit/Safari were never run (also: WASM-SIMD is required by the shipped OCR core; there is no non-SIMD fallback). IndexedDB behaviour in Safari/private mode and on low-storage phones was not tested.
- **Office applications:** Word, Excel and Google Sheets were not available. Files were verified with LibreOffice, python-docx, openpyxl and an Office-package integrity check, which reduce but do not remove the risk of an "unreadable content" error in Microsoft Office.
- **Devices:** no real phone, camera capture, or low-memory behaviour was tested. Large PDFs (50 pages) and images up to 12 MP are limits, not measured capacities.
- **Layout fidelity:** Word/Excel are reconstructions of corrected values, not layout copies; the structured PDF uses standard fonts (non-WinAnsi characters become `?`, counted and reported).
- **One recognition at a time** (one OCR worker); Pause takes effect after the current file.
- **Persistence:** a closed tab loses the workspace unless a project was saved; saved projects may be cleared by the browser if persistent storage is not granted; the portable project file is not encrypted.
- **Deployment:** no deployment was made or tested. Headers (compression, caching, `Service-Worker-Allowed`) for a real host are not configured.
- Main-thread tasks up to 570 ms were observed under 4x CPU throttling (see section 6).

### Real-document result (honest, tiny sample)

Six documents, four of them non-English (Dutch, French ×2, one hosting invoice I did not read closely, likely German) which is **out of scope** (the product is English-only) and showed nothing useful: the fields stay empty or wrong. Of the two English-ish documents after the fixes:

- Flipkart invoice: supplier ✓, issue date ✓, total ✓; customer left empty (was wrong), number empty (document has only an "Order ID").
- OYO receipt: type ✓, date ✓, currency INR ✓, total `Rs 1939` ✓; supplier **wrong** ("Hotel Details", a section heading).

Six documents prove nothing statistically. Treat real-world accuracy as **unknown but visibly worse than the synthetic 98 %**: supplier detection is a first-line heuristic and every guessed field is already flagged "Check it" in the editor.

### Still not fixable here

- **Firefox**: Ubuntu's `firefox` is a snap stub; Mozilla download hosts are blocked. Never run.
- **Real Safari/iOS, real phones, installed-PWA behaviour, real screen readers (NVDA/JAWS/VoiceOver/TalkBack)**: not available. axe-core, keyboard tests and device emulation remain the only evidence.
- **Word / Excel / Google Sheets opening the files**: not available. Files are validated with python-docx, openpyxl, LibreOffice and poppler only.
- **Deployment**: not done (needs your decision and hosting account). The configs above are ready.
- **OCR on throttled CPUs**: CPU throttling does not slow the OCR worker, so recognition times are not a phone estimate. Unchanged.
- **First open offline / ~11.5 MB of vendored files**: inherent to a PWA that must download its program files once.
